# Protocol and feed verification

The decoder uses [Pump's public IDLs at 639b87fb45c3adeffa6f7c4a1bf0cb85e392bf22](https://github.com/pump-fun/pump-public-docs/tree/639b87fb45c3adeffa6f7c4a1bf0cb85e392bf22/idl). Pump and PumpSwap program addresses, instruction discriminators, account positions and event field layouts are read against this revision. Native SOL is normalized to the wrapped SOL mint in events. The feed resolves signers from the required signature prefix of static keys. Address lookup tables supply instruction accounts but cannot supply transaction signers. The event association uses the called program, event authority account and CPI nesting evidence. Missing event and state evidence leaves the quote unknown.

The supported launch configurations use classic SPL Token for legacy creation, or the Token-2022 mint initialization and mint metadata extensions used by ordinary `create_v2`. The decoder marks unknown extensions, Mayhem, cashback, holder rewards and custom fee configurations for review. Canonical curve and pool addresses are derived from the mint, quote and documented PDA seeds. Quoted fees use the event's protocol and creator rates and the pool's LP rate where applicable. Buyback is paid out of the protocol fee. Ordinary PumpSwap effective quote reserves account for signed virtual reserve adjustments, which may reflect fees awaiting sweep. Boosted or ambiguous states cannot produce a supported quote. The decoder leaves a pool's post-trade reserves unknown when multiple operations can change that pool before the transaction's final balances. [Fee sweeps](https://github.com/pump-fun/pump-public-docs/blob/639b87fb45c3adeffa6f7c4a1bf0cb85e392bf22/docs/instructions/SWEEP_FEES.md), [virtual quote reserves](https://github.com/pump-fun/pump-public-docs/blob/639b87fb45c3adeffa6f7c4a1bf0cb85e392bf22/docs/VIRTUAL_QUOTE_RESERVES_FEE_ADJUSTMENT.md).

The ordered adapter subscribes to confirmed transaction logs for both program IDs plus slot heartbeat. It scans complete confirmed blocks with ordered transaction details, then checks finalized block identities before advancing the durable slot. Recent confirmed events restored from the ledger let paper and monitor runs reconcile block replacements after restart. Notifications without a matching hydrated block are observed evidence only. Blocks scanned in backfill or without timely receipts cannot enter trades. A confirmed fork replacement or decode gap marks the feed unhealthy. An archive manifest separates failures retrieving announced blocks from slots omitted by the RPC range query and records missing time or state evidence. Archive block time is modeled observation time and lacks millisecond precision.

Use an RPC provider that serves full confirmed and finalized blocks, both WebSocket program subscriptions and high enough request and bandwidth limits to keep up with the chain. The strict path hit HTTP 429 and notification backlog pressure on the public endpoint. The public monitor configuration uses a separate, deliberately incomplete launch sampler. It filters candidate notifications before using bounded confirmed `getTransaction` hydration and marks samples late. The sampler cannot establish market ordering or feed health for entries, finalize events, or fill archival gaps. A 15 second public mainnet smoke observed 3 launches, 3 bundled trades and 3 hydrated raw transactions at the adapter. Counts vary with traffic and provider limits. [Solana log subscriptions](https://solana.com/docs/rpc/websocket/logssubscribe), [ordered blocks](https://solana.com/docs/rpc/http/getblock), [transaction hydration](https://solana.com/docs/rpc/http/gettransaction).

The public-chain decoder fixtures were retrieved with confirmed-by-finality `getTransaction` from the public Solana RPC on 2026-11-17. Their envelopes identify the original signatures. Fixture redaction removes free-form metadata and nonessential RPC fields while retaining the original slot, transaction outcome, account indices, signer evidence and state bytes used by the decoder. The modified fixtures are decoder test inputs and their transaction signatures cannot authenticate the modified payload. The successful v0 launch and bundled buy at slot 442386434 exercise loaded addresses, inner events, launch-time Token-2022 evidence and exact integer reserve and fee fields. The failed v1 record at slot 467938987 checks that even an emitted create event cannot establish a successful launch when a later instruction fails in the same transaction.

Provider verification is still needed for full ordered continuous capture, positive v1 execution, historical PumpSwap fee sweeps and routed trade completeness. The decoder recognizes the documented direct trade instructions and the same instructions when invoked via CPI. There is no complete tape reconstruction of specialized multi-hop routes, pool boosts or unmodeled fee/configuration changes. Probe matched research coverage before relying on these windows.

Yellowstone is deferred. The reviewed optional client is `@triton-one/yellowstone-grpc@10.0.0` (Apache-2.0), with upstream HEAD `1efaf08688db88915772023d2ee2cd00b398eb65` at review. This release publishes native bindings for Linux x64 GNU/musl and macOS x64/arm64, with no Windows build. Before an adoption, verify authenticated provider access on a supported host, confirmed transaction filters for both programs, exact slot/index ordering, success/loaded-address and inner-instruction reconstruction, ping handling, and the provider's replay retention for `fromSlot` across disconnects. Reconcile provider gaps against finalized ordered history. Deshred and preconfirmation streams lack the required executed success metadata. [Yellowstone protocol and client](https://github.com/rpcpool/yellowstone-grpc/tree/1efaf08688db88915772023d2ee2cd00b398eb65), [client package](https://www.npmjs.com/package/@triton-one/yellowstone-grpc/v/10.0.0).
